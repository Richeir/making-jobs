# 📏 评测（eval）：把"感觉变好了"换成数字

> 2027 最重要的差异化能力不是"会用 AI"，是**能证明 AI 的产出可以用**。
> 能拿出这个证明的人，才有资格批准合并、才有资格把 AI 功能交付给用户。

## 为什么它进面试

AI 放大的是工程判断力的差距：强者提效数倍，弱者更快地生产返工。
区分两者的，就是**有没有验证环节**。

- 允许用 AI 的项目型面试，追问的全是"你为什么这么做""你怎么知道它是对的"；
- SonarSource / Veracode 的年度报告反复说同一件事：AI 生成代码仍高频引入 OWASP 类缺陷。
  "能抓住 AI 的错"已经是一个可量化、可展示的核心竞争力；
- 在 AI 构建那一层，没有 eval 的功能等于**质量不可观测**——你无法解释一次用户投诉，
  也无法证明新版本比旧版本好。面试官只需要问一句"你的准确率是多少"就能判生死。

一句话：**说不清验证方式的 AI 经验，在简历上属于负资产。**

## 核心动作

### 1. 默认不信任，并写出具体的关卡

任何 AI 产出必须经过下列**至少一种**才允许合并：类型检查、lint、测试、静态分析、人工逐行审查。
把这句话变成团队的 CI 门禁，而不是个人习惯。

### 2. 建 eval 而不是靠试 prompt

对高频任务建立：

```
小样本测试集（20–50 条，覆盖边界与失败模式）
  + 打分口径（什么算通过：可断言的标准，不是"看着不错"）
  + 回归基线（当前通过率，任何改动都要对比）
```

离线数据集 + 在线 A/B + LLM-as-judge 三层里，**先有第一层**才有资格谈后两层。
LLM-as-judge 有已知偏差（偏爱长答案、偏爱自家模型风格），要用人工标注校准过才能信。

### 3. 训练检出率：埋雷练习

定期用**已知有缺陷**的 AI 产出测自己，记录检出率。要能一眼挑出这六类：

| 缺陷类型 | 典型形态 |
| --- | --- |
| 幻觉 API | 调一个不存在的库函数，签名看着极合理 |
| 幻觉依赖 | import 一个不存在的包（slopsquatting 是真风险） |
| 边界条件被悄悄改掉 | 原来的 `>=` 变成 `>`，空输入分支被删 |
| 越权 / 注入 | 拼接 SQL、把用户输入直接塞进 prompt 或 shell |
| 竞态 | 拆了锁、把临界区扩到 I/O 上、共享可变状态 |
| **被删掉的测试** | 为了让 CI 变绿而删断言——最阴险的一种 |

### 4. 成本与延迟是评测的一部分

模型档位路由、prompt 缓存、上下文瘦身、批量与小模型前置。
**能给出单位任务成本**（每次调用几分钱、每个任务多少 token、P95 延迟多少）
——这是"做过"和"跑通过 demo"的分界线。

### 5. 明确哪些不能自动化

破坏性操作、数据迁移、合规审计、权限变更。为这些设计**人工确认关口**，
并能说清为什么：它们的失败不可逆，或者责任无法转移给模型。

### 6. 攒可迁移的资产库

规则文件、prompt、脚本、评测集。硬指标：**换工具时能在一天内迁移完成**——不被单一产品锁定。

## 常见失败

- 只有 demo，没有测试集：被问"这个功能上线后错了怎么发现"就哑火；
- 用主观感受代替打分口径："试了几个感觉还行"；
- 把 LLM-as-judge 当客观真值，不做人工校准；
- 只测 happy path：评测集里没有一条对抗样本、没有一条空输入；
- 报不出成本，也报不出返工率变化；
- 让 RAG 变成越权通道：检索层不做权限继承，用户 A 问出了用户 B 的数据。

## 证据怎么准备

一条能连起来讲的链，缺环就补环：

1. **评测集本身**：样本量、覆盖策略、打分口径；
2. **基线与曲线**：v1 → v3 的通过率/准确率变化，每轮改动针对哪一类错误；
3. **错误归因**：一两个"一开始以为是模型不行、其实是检索没做权限过滤"的具体故事；
4. **成本表**：单位任务成本、缓存命中率、降级方案；
5. **一次检出记录**：埋雷练习的成绩，或你从一个 AI PR 里挑出问题的真实 diff；
6. **量化提效**：某功能从 N 人日降到 M 人日，返工率 / 缺陷率 / 评审驳回率怎么变。

清单里"能拿出量化的提效证据"这一条，指的就是这一整套材料。

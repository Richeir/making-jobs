# 🗄️ 数据库原理：闭卷手算

> 门票项。考点不是"用过 ORM"，是**给你一条 SQL 和一张表，你能在纸上算出
> 它走不走索引、锁住什么、会不会死锁**。AI 写的高并发事务，正是靠这套原理才看得出问题。

## 为什么它进面试

模型能替你写 `SELECT`，但替不了你判断。不懂 MVCC 与间隙锁，就发现不了它写的事务
在高并发下会死锁。数据库是后端面试里**追问密度最高**的领域，因为它的答案能分层：
背概念的人到第二层就掉下去。

## 核心动作：每条都要能手推

### 存储引擎：B+ 树 vs LSM-tree

一个偏读、一个偏写。讲清三件事就能过这一关：

- B+ 树：随机写放大（页分裂）、层级即 IO 次数、为什么叶节点要串成链表（范围扫描）；
- LSM-tree：顺序写换读放大、空间放大（多层冗余副本）、compaction 抖动从哪来；
- 选型口径：读多写少且要求低延迟 → B+；写吞吐优先、能容忍读放大 → LSM。

### 索引：给一条 SQL 手算走不走

这是最能当场分出真假的动作。给 `KEY idx(a, b, c)`，你要能判断：

| SQL | 走不走 | 为什么 |
| --- | --- | --- |
| `WHERE a=1 AND c=3` | 只用到 a | **最左前缀**断了 |
| `WHERE a=1 ORDER BY b` | 走，且免排序 | b 在索引里有序 |
| `WHERE b=2` | 不走（或走索引扫描） | 缺最左列 |
| `SELECT a,b FROM t WHERE a=1` | 覆盖索引，**不回表** | 需要的列都在索引里 |

再补两个手感：区分度（选择性）决定索引划不划算；`LIKE '%x'` 与函数包裹列会击穿索引。
**能报出"大致扫多少行"比背概念值钱得多。**

### 事务与 MVCC：把可见性讲成一条线

`undo log` 存历史版本 → 每个事务有 ID → `ReadView` 记录"生成本快照时谁还活跃"
→ 用版本链倒着找第一个对自己可见的版本 → `purge` 决定旧版本何时能清。

把这条线讲清楚，隔离级别就是它的推论：

- **RC**：每条语句生成新 ReadView → 同一事务里两次读不一样（不可重复读）；
- **RR**：事务首次读生成 ReadView 并复用 → 快照一致，但**幻读靠间隙锁补**，不是靠快照本身；
- **串行化**：读也加锁。

### 间隙锁死锁：能画出一个真实场景

经典款：两个事务并发在同一个间隙里做"不存在则插入"（`INSERT ... WHERE NOT EXISTS` / upsert），
各自持有对方的间隙锁，插入意向锁与间隙锁冲突 → 双双阻塞后死锁。
**能在纸上画出两个事务各自锁住了哪段间隙**，这一题就过了。这也是 AI 生成的"读改写"代码最常见的线上事故。

### redo / undo / binlog：两阶段提交

顺序要能背出来并解释为什么：**redo prepare → 写 binlog → redo commit**。

- 崩溃恢复时以 redo 为准 → 为什么不会丢已提交事务；
- 主从为什么会不一致：binlog 与 redo 之间的窗口；
- `binlog` 是 server 层的归档与复制依据（逻辑日志），`redo` 是引擎层的崩溃恢复（物理日志），
  `undo` 是回滚与 MVCC 的版本来源——**三者职责别混，一混就露怯**；
- 半同步与延迟从库各自解决什么（数据安全 vs 误操作兜底）。

### 实操三件套

连接池参数（为什么不是越大越好）、慢查询定位路径、`EXPLAIN` 各字段读法
（type / key / rows / Extra：`Using filesort` 和 `Using temporary` 为什么是警报）。

## 常见失败

- 背得出四个隔离级别，说不出 ReadView 怎么判可见；
- 把 RR 下的"解决幻读"完全归功快照，讲不了间隙锁那一半；
- 说不清覆盖索引为什么免回表；
- redo 和 binlog 的职责互换，两阶段提交顺序说反；
- `EXPLAIN` 只看有没有 `key`，不看 `rows` 和 Extra；
- 只背八股不在真实 SQL 上算：给一条查询估不出扫描量，追问两层就到底。

## 证据怎么准备

- **一次真实的慢查询治理**：原始 SQL → `EXPLAIN` 输出 → 你算出的扫描行数 → 改法 → 前后耗时；
- **一次线上死锁**：`SHOW ENGINE INNODB STATUS` 的死锁日志片段 + 你的归因 + 怎么改的；
- **一次数据不一致事故**：主从延迟或双写窗口，你怎么发现、怎么定责、怎么补的关口；
- **手写一遍迷你 B+ 树或 WAL**：同时是 2.2 工程实践的证据。
